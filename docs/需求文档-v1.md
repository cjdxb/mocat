## 1. 背景与目标

### 1.1 背景

运营商通常会对"无法识别协议类型"的连接做 QoS 限速，而对 HTTP（TCP）、SIP（UDP）等常见协议的连接则通常不限速。
若在转发链路上让 TCP 流量"看起来像 HTTP"、UDP 流量"看起来像 SIP"，中间设备（DPI）就会把连接标记成不限速的类型，从而提升实际转发速率。

可参考的开源实现：

- FakeHTTP：<https://github.com/MikeWang000000/FakeHTTP>（TCP 混淆为 HTTP）
- FakeSIP：<https://github.com/MikeWang000000/FakeSIP>（UDP 混淆为 SIP）

两者的思路都是：在连接建立前后，额外注入若干**伪造的协议报文**（fake packet）。这些报文能被链路上的 DPI 看到，却不会被对端应用当作有效数据（例如用较小的 TTL 让报文在到达对端前过期）。真实业务数据本身不做修改。

### 1.2 目标

开发一套网络转发工具 **mocat**，由两部分组成：

1. **节点（Node）**：负责实际的网络转发，支持多个节点串成链式转发，并在转发链路上发送 FakeHTTP / FakeSIP 伪装报文。
2. **控制端（Controller）**：不参与转发，只负责管理和控制节点，提供 Web 管理界面。

### 1.3 设计原则

- **转发不自己造轮子**：实际的数据转发交给成熟方案（socat、nftables 等），mocat 只负责编排和管理这些方案。
- **核心增量功能**是"模拟 HTTP"和"模拟 SIP"的伪装报文注入。
- 只支持 Linux，架构为 **amd64** 和 **aarch64（arm64）**。
- 开发语言：**Go**（控制端和节点都用 Go）。

## 2. 术语

| 术语 | 说明 |
| --- | --- |
| 控制端（Controller） | 管理节点、下发配置、提供 Web 界面的服务，本身不转发业务流量 |
| 节点（Node） | 部署在 Linux 主机上的代理程序（agent），执行转发和伪装 |
| 转发规则（Rule） | 一条"入口地址:端口 → 出口地址:端口"的转发配置，包含协议（TCP/UDP）和伪装方式 |
| 转发链（Chain） | 由多个节点按顺序组成的转发路径，例如 入口节点 A → 中继节点 B → 目标服务 |
| 跳（Hop） | 链中相邻两点之间的一段连接 |
| 转发后端（Backend） | 实际执行转发的程序或机制，例如 socat、nftables |
| 伪装（Obfuscation） | 在链路上注入 FakeHTTP / FakeSIP 报文 |
| 伪装报文（Fake Packet） | 只给中间设备看、不会被对端当作有效数据的伪造协议报文 |

## 3. 系统架构

```
                       ┌──────────────────────────┐
     管理员 ── 浏览器 ──▶│  控制端 Controller        │
                       │  - Web 管理界面            │
                       │  - REST API               │
                       │  - 节点管理 / 规则编排      │
                       │  - 数据存储                │
                       └──────────┬───────────────┘
                                  │ 控制通道（控制端主动连接节点，TLS + 鉴权）
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        ┌──────────┐        ┌──────────┐        ┌──────────┐
 用户 ──▶│ 节点 A    │══════▶│ 节点 B    │══════▶│ 节点 C    │══════▶ 目标服务
        │ 转发+伪装 │  跳1   │ 转发+伪装 │  跳2   │ 转发+伪装 │  跳3
        └──────────┘        └──────────┘        └──────────┘
   ──▶ 不伪装（用户→入口节点）   ══▶ 节点出站方向，可伪装
                    （业务数据面，不经过控制端）
```

- **控制面**：控制端主动连接各节点的管理端口，用于鉴权、下发配置、拉取状态。
- **伪装位置**：只在节点的**出站方向**（本节点 → 下一跳 / 目标）注入伪装报文；用户 → 入口节点这一段、以及入站方向，本版都不伪装。
- **数据面**：用户 → 节点 → … → 目标，控制端不参与。
- 控制端宕机时，节点应按**最后一次收到的配置**继续工作，不中断转发。

#### 4.1.3 链式转发

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| N-20 | 支持多节点链式转发：每个节点的规则目标可以是下一跳节点的入口端口 | P0 |
| N-21 | 链中由节点发出的每一跳（节点→下一跳节点、末节点→目标）都可以单独设置伪装方式（不伪装 / FakeHTTP / FakeSIP）；用户→入口节点这一跳不伪装 | P0 |

#### 4.1.3a 伪装的核心约束：先伪装，后发送业务数据

> **硬性要求**：启用伪装的连接 / 流，在**第一个真实业务报文**发出之前，必须已经发出伪装报文。否则 DPI 可能先看到真实流量，把连接识别为未知协议并限速。宁可不转发，也不能让未伪装的业务数据先发出去。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| N-25 | **TCP**：伪装报文必须在握手完成、任何业务数据（含 TCP Fast Open 携带在 SYN 中的数据）发出之前发出。沿用 FakeHTTP：截住对端的 SYN-ACK，先发伪装报文，再放行 SYN-ACK，本机收到 SYN-ACK 后才可能发出数据。伪装出站的连接需禁用 TCP Fast Open | P0 |
| N-26 | **UDP**：每个新流的第一个业务报文必须在伪装报文之后发出。沿用 FakeSIP：截住流的第一个报文，先发伪装报文，再放行原报文 | P0 |
| N-27 | **失败即阻断（fail-closed）**：伪装进程未就绪、异常退出、或伪装报文发送失败时，对应规则的流量必须被拦住（不转发），不能绕过伪装直接放行。mocat 生成的 NFQUEUE 规则不使用 `bypass` | P0 |
| N-28 | **启动顺序**：启用一条规则时，必须先启动伪装进程并确认其就绪，再安装 NFQUEUE 规则，最后才开启转发（socat 监听 / DNAT 规则）。停止时顺序相反：先停转发，再撤伪装 | P0 |
| N-29 | **不得跳过伪装**：伪装进程中会导致"跳过伪装、直接放行"的逻辑（如 FakeHTTP 跳数估算判定对端为本地时不注入），在 mocat 管理的规则上不能生效；无法避免时需在配置校验阶段拒绝或告警 | P0 |
| N-2A | 规则启用时，清除该规则相关的已有 conntrack 条目 / 已有连接，避免在伪装生效前已建立的连接继续传输未伪装的数据 | P0 |
| N-2B | 因伪装失败而被拦截的连接 / 报文需计数，并上报控制端、在 Web 上提示 | P1 |

#### 4.1.4 伪装：模拟 HTTP（FakeHTTP，作用于 TCP）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| N-30 | 对指定 TCP 连接，在三次握手完成前后注入伪造的 HTTP 请求报文，使链路 DPI 将连接识别为 HTTP | P0 |
| N-31 | 伪装报文不能被对端当作有效数据：沿用 FakeHTTP 的做法，使用较小 TTL 让报文在到达对端前过期；TTL 可配置 | P0 |
| N-32 | 可配置伪造 HTTP 请求的 Host（对应 FakeHTTP `-h`），并提供合理默认值；可选：用自定义二进制文件作为伪装载荷（对应 `-b`） | P0（Host）/ P1（自定义载荷） |
| N-33 | 可配置每条连接注入的伪装报文重复次数（对应 `-r`） | P1 |
| N-34 | 伪装作用范围：只作用于**本节点发出的出站连接**（即本节点→下一跳 / 目标这一跳）；入站方向不做 | P0 |
| N-35 | 只对 mocat 管理的规则对应的连接生效，不影响主机上其他流量 | P0 |
| N-36 | 支持 FakeHTTP 的跳数估算（`-y` 按百分比动态调整 TTL，`-g` 关闭估算），以便计算合适的 TTL | P1 |

#### 4.1.5 伪装：模拟 SIP（FakeSIP，作用于 UDP）

| --- | --- | --- |

| N-43 | UDP 流的划分沿用内核 conntrack：conntrack 条目超时后，新数据视为新流并重新注入 | P0 |

| 编号 | 需求 | 优先级 |

## 5. 非功能需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| NF-01 | 平台 | 只支持 Linux，架构 amd64、aarch64；最低内核版本在概要设计中确定（需支持 nftables 和 NFQUEUE） |
| NF-02 | 依赖 | 运行时依赖尽量少；fakehttp / fakesip 静态编译后随包发布；系统需提供的依赖（nft、socat）在文档中列出，并在启动检查中提示 |
| NF-03 | 性能 | 伪装只处理连接 / 流的起始报文，不应明显影响转发吞吐；nftables 后端下吞吐接近内核直接转发 |
| NF-10 | 规模 | 设计规模：节点数 < 50，整个系统合计并发连接数 < 100 |
| NF-04 | 资源 | 节点空载内存占用应较小，适合在低配 VPS、ARM 小主机上运行（具体指标在测试阶段确定） |
| NF-05 | 可靠性 | 控制端不可用时，节点按缓存配置继续转发；节点重启后自动恢复 |
| NF-06 | 安全 | 节点管理端口、控制端 Web 默认只用 HTTPS / TLS；Token、密码等敏感信息不打印到日志，控制端存储时加密或哈希 |
| NF-07 | 可维护性 | 结构化日志，支持日志级别设置；所有组件都有 `--version` 输出 |
| NF-08 | 隔离性 | mocat 创建的 nftables 规则放在独立的表中，不修改、不清空用户已有规则 |
| NF-09 | 许可 | FakeHTTP / FakeSIP 为 GPL-3.0。只以独立进程方式调用、不把其代码链接进 mocat；随包分发时附带其许可证文本和对应源码（或源码获取方式），见附录 A |

## 6. 第一版范围外（不做）

- Windows、macOS 等非 Linux 平台。
- 业务数据加密、自定义隧道协议（数据按原样转发）。
- "客户端 + 服务端真实握手"模式（见第 7 节，作为后续扩展）。
- 负载均衡、多路径、故障自动切换。
- 多用户、角色权限体系。
- TCP ↔ UDP 协议转换。
- 用户 → 入口节点这一段的伪装。
- 入站方向的伪装（只做节点出站方向）。
- 管理在 NAT 后、控制端无法直接访问其管理端口的节点。

## 7. 后续扩展方向（第一版需预留）

### 7.1 真实握手模式

第一版只在链路上**单向注入**伪装报文。以后可能增加"客户端 + 服务端"模式：相邻两个节点之间做一次**真实的 HTTP / SIP 握手**（例如真的发 HTTP 请求并收到 HTTP 响应，或完成 SIP 信令交互），之后再传输业务数据，伪装效果更好。

第一版为此需要预留：

- 伪装方式做成插件接口（N-53），以后可以新增"真实握手"类型，而不改动转发和管理逻辑。
- 规则模型中的"伪装配置"按"类型 + 参数"组织，方便以后加新类型。
- 链路中每一跳的两端都能识别对方是 mocat 节点（控制端已经知道整条链的拓扑，可以在下发时为两端生成匹配的配置）。

### 7.2 其他

- 更多协议模拟（如 TLS ClientHello、QUIC 等）。
- 节点在线升级。
- Prometheus 指标导出。

## 9. 验收标准（第一版）

1. 在 amd64 和 arm64 的 Linux 主机上都能安装并运行控制端和节点。
2. 在 Web 上新建节点，并按提示命令在目标主机启动节点后，控制端能连上节点，节点在 Web 上显示为在线；用错误 Token 访问节点管理端口会被拒绝。
3. 通过 Web 配置单节点 TCP 和 UDP 转发，用 socat 和 nftables 两种后端都能正常转发。
4. 通过 Web 编排一条至少 3 个节点的链（A → B → C → 目标），TCP 和 UDP 链都能端到端连通。
5. 启用 FakeHTTP 后，在节点出口抓包（如 tcpdump）可以确认：每条出站连接上，伪造 HTTP 请求报文都出现在**第一个业务数据报文之前**，且对端应用收到的数据与未启用时一致。
6. 启用 FakeSIP 后，抓包确认每个新 UDP 流的伪造 SIP 报文都出现在**第一个业务报文之前**，且业务数据不受影响。
7. 手动杀掉伪装进程后，对应规则不再有任何未伪装的业务报文发出（抓包为零），其他规则不受影响；伪装进程自动重启后转发恢复。
8. 停止控制端后，节点上已有的转发继续工作；节点重启后按缓存配置恢复。
9. 删除规则或停止节点后，系统中不残留 mocat 创建的 nftables 规则和子进程。
10. 主机上与 mocat 无关的流量和已有 nftables 规则不受影响；节点上与 mocat 规则无关的 TCP / UDP 连接不会被注入伪装报文。
11. Web 上能看到每条规则的上下行流量和当前连接数，数值与实际传输量基本一致。

## 附录 A：FakeHTTP / FakeSIP 复用评估

### A.1 项目概况

| 项目 | FakeHTTP | FakeSIP |
| --- | --- | --- |
| 仓库 | <https://github.com/MikeWang000000/FakeHTTP> | <https://github.com/MikeWang000000/FakeSIP> |
| 许可证 | GPL-3.0 | GPL-3.0 |
| 语言 / 构建 | C99，Makefile，支持 `STATIC=1` 静态编译、`CROSS_PREFIX` 交叉编译 | 同左 |
| 依赖库 | libnetfilter_queue、libnfnetlink、libmnl | 同左 |
| 最新版本（调研时） | 0.9.18（2025-06-24） | 0.9.1（2025-07-29） |
| 成熟度 | 约 60 次提交，社区使用较多 | 约 5 次提交，项目较新 |

### A.2 工作原理（与本项目相关的部分）

- **FakeHTTP**：用 nftables 把 TCP 的 SYN / SYN-ACK 报文送入 NFQUEUE。对出站连接，收到对端的 SYN-ACK 后，用 raw socket 按当前序列号发出伪造的 HTTP 请求报文，再放行原报文。伪装报文使用较小 TTL，可根据收到报文的 TTL 估算跳数自动调整。
- **FakeSIP**：用 nftables 把每个 UDP conntrack 流的前 5 个报文送入 NFQUEUE，在业务报文前发出伪造的 SIP 报文，TTL 处理与 FakeHTTP 相同。
- 两者自带规则都用 `queue ... bypass`，且打开 NFQUEUE 时设置了 `NFQA_CFG_F_FAIL_OPEN`（队列满时直接放行）。这是"失败即放行"的设计，与本项目 N-27 的"失败即阻断"相反，需要处理（见 A.3）。
- 两者都用 fwmark（`-m` / `-x`）标记自己发出的报文，避免重复处理。

### A.3 直接使用存在的问题

| 问题 | 说明 | 解决办法 |
| --- | --- | --- |
| 作用范围过大 | 自带规则只能按网卡（`-i` / `-a`）选择，不能按端口或 IP 过滤，会影响主机上所有 TCP / UDP 连接，不满足 N-35 | 用 `-f` 跳过其自带规则，由 mocat 在自己的 nftables 表中生成精确规则（按规则的目标 IP / 端口匹配），只把这些报文送入对应队列 |
| 不支持多实例 | 自带规则的表名固定（`fakehttp` / `fakesip`），启动时会先删表，多个实例会互相覆盖 | 用 `-f` 后不再创建自带表；每个实例使用不同的队列号（`-n`）和 fwmark（`-m`）。实际能否多实例共存需验证 |
| 参数是进程级的 | Host、TTL 等参数作用于整个进程，不能按连接区分 | 按参数组合分组，一组参数一个进程（N-54） |
| 需要 C 依赖 | 依赖 libnetfilter_queue 等库 | 我们自己固定版本、从源码静态编译 amd64 / arm64 版本，随包发布 |
| 失败即放行 | 伪装进程不在时 `bypass` 会让报文直接放行；队列满时 `FAIL_OPEN` 也会直接放行，都可能让未伪装的业务报文先发出 | mocat 生成的规则不加 `bypass`（进程不在时内核直接丢弃报文）。`FAIL_OPEN` 在上游代码中写死：本项目连接数很少，队列满的概率低，但仍需在 PoC 中评估；必要时修改上游代码去掉该标志（修改版按 GPL-3.0 公开源码） |
| 可能跳过伪装 | FakeHTTP 在估算出对端跳数 ≤ TTL 时会判定为"本地对端"而不注入，连接照常放行 | 规则使用固定 TTL 并关闭跳数估算（`-g`），或在 PoC 中确认该判定在实际场景下不会触发；需满足 N-29 |

### A.4 结论

**可以复用，方式是"作为独立进程调用"，不把其 C 代码编进 mocat。**

- **许可证**：mocat（Go）与 fakehttp / fakesip 是各自独立的程序，通过命令行参数和 NFQUEUE 协作，mocat 本身不受 GPL-3.0 约束。分发时需要附带二者的 GPL-3.0 许可证文本，并提供对应的源码（或源码获取方式）。如果以后改成用 cgo 链接其代码，mocat 整体需要按 GPL-3.0 发布。
- **修改**：优先不修改上游代码。如果必须修改（例如修复多实例问题），修改后的版本同样按 GPL-3.0 公开源码。

### A.5 开发前需要验证的事项（技术验证 PoC）

1. 使用 `-f` 时，多个 fakehttp（或 fakesip）实例使用不同队列号能否同时运行，互不干扰。
2. **socat 后端**：socat 发起的出站连接能否正常触发 FakeHTTP 的出站逻辑，并在链路上抓到伪装报文。
3. **nftables DNAT 后端**：被转发（非本机发起）的连接能否正确触发伪装，伪装报文的源地址、序列号是否正确（需关注与 DNAT / SNAT 的处理顺序）。
4. FakeSIP 在出站方向是否会把原始报文重复发送一次；若有，评估影响或改用其他方式。
5. 两者在 amd64、arm64 上静态编译是否顺利。
6. **先伪装、后业务数据（N-25 / N-26）**：在 socat 和 DNAT 两种后端下抓包，确认每条 TCP 连接、每个 UDP 新流的伪装报文都在第一个业务报文之前发出，包括伪装报文按 `-r` 重复发送的情况。
7. **失败即阻断（N-27）**：杀掉伪装进程、或人为制造队列积压时，确认没有未伪装的业务报文漏出；评估 `FAIL_OPEN` 的实际风险。

如果第 2、3 项验证不通过，再考虑参考其原理用 Go 自行实现伪装模块（需注意不要照搬其代码，以免受 GPL 约束）。
